# 协议格式

## BLE 小程序协议

USART2 连接 VG6328（PA2/PA3，115200 8N1；2026-09-20 与 4G 模组对调，占哪一路由 `APP_CFG_BLE_UART_ID` 决定）。透明通道帧为 2 B 大端载荷长度、最多 17 B 载荷和 CRC8 `0x07`，总长不超过 20 B；长 JSON 以 14 B 数据分片，并携带 1 B 序号和 2 B 总长度。命令为 `auth/params/get/set/ping/nak/reboot`，设备主动发送 `data`；认证成功响应包含 `ok=true` 与 SN，断链立即清除认证和半包状态。

USART1 当前是开发调试通道，承载 AT-only 输入、启动信息、采样诊断和异步日志。它不是具备寻址、确认、重传与帧同步的产品通信协议。

## 物理层

| 项目 | 值 |
|---|---|
| 外设 / 引脚 | USART1；`PA9` TX、`PA10` RX |
| 串口参数 | 115200，8N1，无流控，3.3 V TTL |
| 接收 | 逐字节中断；64 B RX 环形缓冲；`USART1_IRQn` 优先级 5 |
| 同步发送 | `BSP_print*()`，只用于启动信息与少量诊断 |
| 异步发送 | 512 B TX 环形队列，USART1 发送中断搬运；用于日志与 AT 响应 |
| 文本编码 | 运行期字符串全部为 ASCII 英文，行尾统一 `\r\n` |

## AT 输入

解析器在 Service 层 `App/service/svc_at.c`（只解析），统一命令请求与结果模型在
`App/app_command/app_command.h`，命令的**执行与回复**由 App 层
`App/app/command_dispatch.c`（`App_Command_Dispatch()`）负责。参数读写落在
`AO_Store` 上异步完成，因此调试口不会因为写 EEPROM 而卡住。

命令形态按 V.250 / 3GPP 27.007 的常规约定：**`AT` 前缀 + `?` 读 + `=` 写 + `=?` 测试**，
响应是 `OK` / `+<参数名>:"<值>"` / `+<参数名>:(<最大长度>)` / `+CME ERROR:<n>`。

> [!note] 2026-09-27 接口改写：旧的自定义写法已删除
> 改写前的 `at` / `sn?` / `sn=值` / `cfg?` / `cfg!` / `i2c?` **不再兼容**（缺 `AT+` 前缀、
> `!` 不是 AT 语法元素、错误码用自造的 `+err:<n>`、`ok` 大小写也与标准不符）。
> 同一次改写还删掉了「裸 `at` 不带行尾也回 `ok`」的捷径——它会让 `AT+SN?` 的前两个字符
> `AT` 触发误判。**现在所有命令都必须以 CR 或 LF 结尾。**

### 命令一览

| 请求 | 响应 | 说明 |
|---|---|---|
| `AT` | `OK\r\n` | 握手（大小写不敏感，但必须带 CR/LF） |
| `AT+<参数名>?` | `+<参数名>:"<值>"\r\nOK\r\n` | 读**字符串型**参数；值取自 RAM 影子，**不访问总线** |
| `AT+<参数名>?`（数值型） | `+<参数名>:<值>\r\nOK\r\n` | 读**数值型**参数（`TRANSINTVL`）：**值不带引号** |
| `AT+<参数名>="<值>"` | `OK\r\n` | 写参数；立即改内存影子，落盘异步进行。**身份类参数（当前 `SN`）只允许串口写**，云端写回 `+CME ERROR:4`；`SN` 写成功且**值真的变了**时会自动重启（见下） |
| `AT+<参数名>="<值>"`（不带引号） | `OK\r\n` | 引号可省：`AT+SN=VWA2608A0020` 同样受理 |
| `AT+<参数名>=?` | `+<参数名>:(<最大长度>)\r\nOK\r\n` | 测试形式：报告该字段可写的最大字符数（容量 −1） |
| `AT+TRANSINTVL?` | `+TRANSINTVL:<分钟>\r\nOK\r\n` | 查周期上报间隔（分钟，1~20；数值型，不带引号） |
| `AT+TRANSINTVL=<1..20>` | `OK\r\n` | 写周期上报间隔（分钟）：**掉电保存**、**改完立即生效** |
| `AT+VER?` | `+VER:"<版本>","<编译日期>"\r\nOK\r\n` | 查询固件版本与编译日期 |
| `AT+CFG?` | `+CFG:<8 个逗号分隔字段>\r\nOK\r\n` | 参数存储运行状态（**位置式**，见下表） |
| `AT&F` | `OK\r\n` | 全部恢复编译期默认值并落盘（`config_version` 继续自增） |
| `AT+RST` / `AT+REBOOT` | `OK\r\n` | **重启设备**：先回 `OK`，**延时**（≥500 ms，最多 5 s）后复位，见下 |
| `AT+BLESVCUUID?` | `+BLESVCUUID:"<UUID>"\r\nOK\r\n` | 查 BLE 服务 UUID（= 参数 `uuid`，2026-09-28 新增；**回显名就是命令名**，见下） |
| `AT+I2C?` | 先 `OK\r\n` | 受理 I2C 总线扫描；结果随后以 `+I2C:<地址>` URC 上报，末尾 `+I2C:END` |
| 其他非空行 | `ERROR\r\n` | 收到 CR/LF 后判断，不回显输入 |
| 空行 | 无 | 静默忽略 |
| 非 CR/LF 控制字符 | `ERROR\r\n` | 不解析、不回显 |

参数名（**7 个**，大小写不敏感，响应里统一回大写）：`SN`、`PIN`、`UUID`、`DEVNAME`、`MODEL`、`BATCH`、`TRANSINTVL`。
其中前 6 个是**字符串型**（读回带引号、`=?` 报可写字符数），`TRANSINTVL` 是**数值型**业务参数
（周期上报间隔，分钟，1~20：读回不带引号、`=?` 报范围 `(1,20)`、写越界回 `+CME ERROR:2`）。
参数值区分大小写（SN/名称类身份信息必须原样）。行长度上限由 `APP_CFG_AT_LINE_MAX`（64）决定，
超限的整行会被丢弃并回 `ERROR`（**不是**静默——但现场看起来就是「这条命令没生效」，
因此发长命令时务必确认长度）。

> [!warning] `NAME` 是**退役参数**（2026-09-28）：广播名就是 `SN`
> 产品决定**蓝牙广播名 = 设备 SN**（用户 2026-09-28 确认），因此 `AT+NAME?` / `AT+NAME="…"` /
> `AT+NAME=?` 三种形态一律回 `+CME ERROR:1`（= 没有这个名字），要读广播名请用 `AT+SN?`。
> 参数槽位本身**没有删除**：记录按 id 定位字段，删中间一项会让后续字段整体错位、介质里的
> 旧记录被解码到错误字段上（见 `App/service/svc_param.h` 的退役槽位 NOTE）。
> 判据在 `SVC_Param_IsRetired()`，命令层在读写测试三处统一挡掉。

> [!important] 写权限：**身份类参数只允许串口写**（2026-09-28）
> 当前身份类参数有**两个**：
> - `SN` —— 平台 MQTT 主题里的 `deviceId` + 蓝牙认证应答里的 `sn`；
> - `UUID` —— BLE 服务 UUID，**每台唯一**，启动时写进 VG6328，手机小程序靠它认设备。
>
> 它们都是「产线写一次、之后不该被远程改」的东西，因此按**来源**分权：
> | 通道 | 读（`AT+SN?` / `AT+BLESVCUUID?`） | 写（`AT+SN="…"` / `AT+UUID="…"`） |
> |---|---|---|
> | 串口 | ✅ | ✅（产线唯一入口） |
> | 云端（4G `command` 主题） | ✅ | ❌ 回 `+CME ERROR:4` |
> | 蓝牙小程序 | ✅（认证应答里的 `sn` 字段） | ❌ 本来就不支持写参数 |
>
> 判定在 `App/app/command_dispatch.c` 的 `writeAllowedFrom()`，身份类参数列在 `kIdentityParams[]` 里；
> 加新的身份参数（如 `BATCH`）只需往那张表补一个 id（**写入权限、变更判定与自动重启三处会一起生效**）。
> **为什么这么严**：身份写错是**静默故障**——`SN` 错一个字符，`+MQTTSUBACK` 照样返回、
> 平台一条命令都收不到（本仓库已踩过一次，见 [[08-改动日志]] `#51`）；
> 而云端一旦被误操作/盗用就能**批量改掉设备身份**。
>
> NOTE (身份类 ≠ 设备号类)：**只有 `SN`** 还要过一道"值校验"（字符集/长度/出厂哨兵，
> 因为它的值会嵌进 MQTT 主题）；`UUID` 不套那套规则——它的默认值就是合法值，
> 拿设备号判据去查会被误判成"产线没刷"而拒写。两者的分工见 `isIdentityParam()` 与 `isDeviceIdParam()`。
>
> **写成功后会自己重启**（2026-09-28）：`AT+SN="新值"` / `AT+UUID="新值"` 且**值真的变了**时，
> 固件会请求一次复位——由 `AO_System` 延时执行（先等参数落盘、再复位，见 [[04-任务调度]]），
> 串口上依次出现：
>
> ```text
> system: reboot requested by identity, waiting for reply+store
> system: rebooting now, src=identity waited=612 ms
> ```
>
> - **写回原值（值没变）不会重启**，所以产线脚本可以重复跑；
> - **为什么不立刻复位**：`OK` 只是「已受理」，参数还在异步落盘；立刻复位会让新 SN 丢掉；
> - **为什么必须重启**：`SN` 是设备身份（`deviceId`）。MQTT 的 `clientId` 与全部主题是
>   连接计划启动时拼好的，只改内存不会重新订阅，设备会停在「旧身份」的世界里；
>   蓝牙侧也有已认证的会话需要作废。
>
> **值也有闸**：写入侧 `SVC_Param_IsValidDeviceId()` 会拒掉空值、含 `/` `+` `#` 空格等
> 非法字符、以及**仍等于出厂默认值**（= 产线没刷）的写法，统一回 `+CME ERROR:2`；
> 启动侧用同一个函数判，不合法就**拒绝启动 4G**（详见下面的「设备标识」一节）。

> [!warning] `AT+RST` 是**延时复位**，不是"回完就立刻重启"
> 两个拼写等价：`AT+RST`（平台规则文档里的名字）与 `AT+REBOOT`（本工程自己的叫法，与 BLE 侧一致）。
> 只认**裸命令**——`AT+RST=1`、`AT+REBOOT?` 都不受理（会走普通的 SET/TEST 分支回错误码）。
>
> 收到命令后设备**先回 `OK`**，然后在满足下面三个条件后复位（由 `AO_System` 执行，见 [[04-任务调度]]）：
> ① 至少过了 `APP_CFG_SYSTEM_REBOOT_MIN_DELAY_MS`（500 ms）；
> ② 参数已经落盘（`App_Store_IsIdle()`）；
> ③ 上行的 `command/reply` 已经发出去（`Modem_IsUplinkIdle()`）。
> 若 5 s（`APP_CFG_SYSTEM_REBOOT_MAX_WAIT_MS`）内条件仍不满足，**到点照样复位**。
>
> **为什么必须这样**：复位会丢掉 UART 发送环里的字节、打断 EEPROM 写入、掐断还没发出去的
> MQTT PUBLISH。就地复位会让「平台判指令超时 + 串口无输出 + 刚改的参数丢失」三件事同时发生，
> 而设备已经重启，两边现象对不上——是最难查的一类现场。
>
> 上板可见的证据（串口，复位前最后几行）：
> ```text
> [W 123456] system: reboot requested by cloud, waiting for reply+store
> OK
> [W 124068] system: rebooting now, src=cloud waited=612 ms
> ```
> 复位后启动横幅的 `reset` 行会显示 `SOFT (software reset)`。

> [!note] 平台（4G）侧的命令现状
> - **已实现**：`AT`、`AT+VER?`、`AT+CMD?`（返回本设备命令表，当前是 `+CAD:…` 格式）、
>   `AT+<参数名>?` / `="<值>"` / `=?`、`AT+TRANSINTVL?` / `AT+TRANSINTVL=<1..20>`、
>   `AT+CFG?`、`AT&F`、`AT+I2C?`、**`AT+RST`**（重启设备，回 `OK` 后延时复位）。
> - **未实现**：「设置上报主题」与 `AT+GMR` / `AT+GSLP`，收到回失败应答
>   （`ok:false` + `error:"ERROR"`，见 [[11-平台接口需求]] 1.4）。
> 需求与待平台确认项见 [[11-平台接口需求]]。

### 错误码

| 响应 | 触发条件 |
|---|---|
| `ERROR\r\n` | 命令不认识：缺 `AT` 前缀、参数名/命令名拼错、`=` 后面是空值 |
| `+CME ERROR:1\r\n` | 参数名不在 7 个之列（读写与测试形式都适用）；**退役参数 `NAME` 同此码** |
| `+CME ERROR:2\r\n` | 值为空或超长（超过了该字段的容量）；或**数值型参数越界**（`AT+TRANSINTVL=0` / `=21`） |
| `+CME ERROR:3\r\n` | 参数存储还没就绪（上电加载未结束，此时改会被随后的读取覆盖）；`AT&F` 同理 |
| `+CME ERROR:4\r\n` | **该来源无权写这条参数**：身份类参数（当前 `SN`）只允许串口写，云端写回这个码，且**不写进影子** |
| `+CME ERROR:5\r\n` | `AT+I2C?`：已有扫描在跑，或存储未就绪 / 已关闭 |

> [!warning] `OK` 只代表「已受理」，不代表「已写进 EEPROM」
> 写参数是先改内存、再由 `AO_Store` 异步落盘。真正的结果看日志：
> `store: saved ver=<版本> seq=<槽序号> slot=<A|B> <字节数> B` 表示落盘并**回读校验**通过；
> `store: save failed (...), change kept in RAM only` 表示这次修改只在内存里，掉电会丢。

### `AT+CFG?` 字段含义

响应是**位置式**逗号分隔，顺序固定（只允许在表尾追加新字段）：

```text
+CFG:rdy,present,loaded,dirty,ver,seq,ok,fail
OK
```

> [!note] 读/测试/`AT+CFG?`/`AT+VER?` 的响应都以最终 `OK` 收尾
> 2026-09-27 起，除写命令外，查询类响应也在参数行之后补一行 `OK\r\n`（见 [[08-改动日志]] `#47`）。
> 目的是让串口与 4G 共用同一串 AT 文本：串口原样打印，4G 直接把它当 `data` 包进 `command/reply`。

| 位置 | 字段 | 含义 |
|---:|---|---|
| 1 | `rdy` | 启动加载阶段是否已结束（0 时所有写命令都回 `+CME ERROR:3`） |
| 2 | `present` | EEPROM 是否应答过（0 = 器件不在或总线不通） |
| 3 | `loaded` | 当前值是否来自介质上的有效记录（0 = 用的是编译期默认值） |
| 4 | `dirty` | 有改动还没落盘 |
| 5 | `ver` | `config_version`，每次成功保存自增 |
| 6 | `seq` | 最近一次保存写入的槽序号（A/B 双槽交替） |
| 7 / 8 | `ok` / `fail` | 成功保存次数 / 失败次数（诊断） |

单字符命令 `g/h/s/x/d/?` 已删除。采样由 `App_start()` 在上电时自动启动，不通过调试命令控制。

## 4G 下行命令（平台 `command` 主题）

平台通过 EMQX 把 AT 命令下发到设备，报文规则见项目文档《基于ESPv5自定义的基础AT指令集-固件对接平台规则.md》。**设备侧支持的命令就是上面《命令一览》里的那几条**，4G 与串口共用同一套语义、同一个解析器和同一个执行分发器——云端发 `AT+SN?` 与串口敲 `AT+SN?` 走的是同一条代码路径。

### 主题

**前导 `/` 按主题（用途）逐条给**（2026-09-28 订正）：平台侧存在**两个互不相干的主题空间**——
**数据上报空间**（平台属性上报页原文要求设备发布到 `/{productId}/{deviceId}/properties/report`，**带** `/`）
与**命令/属性交互空间**（平台「AT 控制主题模板」「回复主题模板」写的都是 `{productId}/{deviceId}/…`，**不带** `/`，
命令与它的回复在这一格里闭环）。设备侧照这个事实落成**一条主题一个宏**
（`app_config.h` 的 `APP_CFG_MODEM_TOPIC_PREFIX_*`，与 `modem_component.c` 的 `kTopicPrefix[]` 一一对应，有编译期护栏）：

| 前缀宏（`app_config.h`） | 主题 | 当前值 |
|---|---|---|
| `APP_CFG_MODEM_TOPIC_PREFIX_REPORT` | `properties/report`（数据上报） | `"/"`（带） |
| `APP_CFG_MODEM_TOPIC_PREFIX_READ` | `properties/read` | `""`（不带） |
| `APP_CFG_MODEM_TOPIC_PREFIX_READ_REPLY` | `properties/read/reply` | `""` |
| `APP_CFG_MODEM_TOPIC_PREFIX_WRITE` | `properties/write` | `""` |
| `APP_CFG_MODEM_TOPIC_PREFIX_WRITE_REPLY` | `properties/write/reply` | `""` |
| `APP_CFG_MODEM_TOPIC_PREFIX_INVOKE` | `function/invoke` | `""` |
| `APP_CFG_MODEM_TOPIC_PREFIX_STATE` | `state-check` | `""` |
| `APP_CFG_MODEM_TOPIC_PREFIX_STATE_REPLY` | `state-check/reply` | `""` |
| `APP_CFG_MODEM_TOPIC_PREFIX_COMMAND` | `command`（AT 命令入口） | `""` |
| `APP_CFG_MODEM_TOPIC_PREFIX_COMMAND_REPLY` | `command/reply`（AT 命令回复） | `""` |

按当前值拼出来是（`productId` = `sensor-product`、**`deviceId` = 参数 `sn`** —— 见下面的「设备标识」一节）：

```text
设备订阅（收）： sensor-product/<SN>/properties/read
                 sensor-product/<SN>/properties/write
                 sensor-product/<SN>/function/invoke
                 sensor-product/<SN>/state-check
                 sensor-product/<SN>/command               ← 平台 AT 命令入口（实测收到过）
设备发布（发）： /sensor-product/<SN>/properties/report     ← 周期上报（唯一带 `/` 的）
                 sensor-product/<SN>/properties/read/reply
                 sensor-product/<SN>/properties/write/reply
                 sensor-product/<SN>/state-check/reply
                 sensor-product/<SN>/command/reply         ← AT 命令回复（**不带** `/`）
```

### 设备标识（`deviceId`）

**`deviceId` 就是参数 `SN`**（2026-09-28 起，不再是编译期宏）：

| 项 | 说明 |
|---|---|
| 取值 | `AO_Modem` 构造时取 `App_Store_Value(SVC_PARAM_BLE_SN)`（指向参数影子，永远是最新值） |
| 用途 | MQTT 的 `clientId` + 上面 10 条主题里的 `deviceId` + 蓝牙认证应答里的 `sn`（**一个值走天下**） |
| 谁写 | **只有串口**（`AT+SN="<值>"`）；云端只能读回（见上面的写权限警告框） |
| 合法性 | `SVC_Param_IsValidDeviceId()`：非空、字符集 `A-Z a-z 0-9 - _ .`、长度 <24、**且不等于出厂默认值**（= 产线没刷） |
| 未配置时 | `AO_Modem` **拒绝启动 4G**，串口打 `modem: device SN unusable reason=… pos=… ch=0x… len=… -> 4G disabled; provision it: AT+SN="<device-id>"` |
| 改了之后 | 自动重启；重启后若模组仍留着旧 MQTT 会话，连接计划会用 `AT+MQTTCFG?` 读回模组的 clientId 与当前 `SN` 比对，**不一致就不复用旧会话**，重建后 `clientId` 才是新的（见 [[08-改动日志]] `#71`） |

`reason` 码来自 `SVC_Param_CheckDeviceId()`，写入被拒（`+CME ERROR:2`）时日志也用同一套：

| reason | 含义 | 常见成因 |
|---:|---|---|
| 0 | 合法（不会出现在拒绝日志里） | — |
| 1 | 空串 | `AT+SN=""` |
| 2 | 仍是出厂默认值 = 产线没刷 | 直接上电、没刷过 SN |
| 3 | 长度 ≥ 24 | 抄错/粘多了 |
| 4 | 含非法字符（`pos` = 下标、`ch` = 那一个字节） | **引号里带了空格**、用了**中文全角引号**`“ ”`、或粘进了别的字符 |

> [!tip] 被拒时怎么一眼定位
> 日志形如 `cmd: sn rejected reason=4 pos=12 ch=0x20 len=13`：
> `pos=12`（第 13 个字符）、`ch=0x20`（**空格**）—— 一眼就知道引号里多打了个空格。
> 若 `ch=0xE2`/`0xEF` 之类的高位字节，几乎可以断定是**中文标点/全角字符**混进来了
> （中文输入法下的引号 `“ ”` 很常见）。**应急办法：发不带引号的 `AT+SN=sf-test-0001`**
> —— 解析器两种写法都收，正好用来排掉"引号本身是中文的"这一类问题。

> [!important] 为什么宁可不上线，也不拿默认值去连
> 非法/默认值拼出来的 `sensor-product//command` 在 MQTT 里**是合法主题**，
> 模组订阅还会回 `+MQTTSUBACK`，只是永远收不到平台的消息——**静默失效**，
> 与 `#51` 那次踩的坑同类。同理，**所有设备共用出厂默认值 = 共用同一个 `clientId`**，
> 同批设备同时上线会互相顶掉，现场表现为「设备随机掉线」。所以两道闸都要有：
> 写入时拒脏值（`+CME ERROR:2`）、启动时拒上线。
>
> 另外：这台设备的 `SN` 改了，**平台侧那台设备的 `deviceId` 必须同步改成同一个值**
> （含大小写），否则设备订的主题平台不认；而且改 `SN` = **换身份**，
> 平台侧旧绑定的数据会挂空。详见 [[11-平台接口需求]] 1.1。

> [!warning] 前缀口径必须与**平台页面**一致，否则症状是「订阅成功但没有消息」
> - **平台侧证据（两个方向各自独立，别互相反推）**：
>   - **命令/交互空间（不带 `/`）**：「AT 控制主题模板」`{productId}/{deviceId}/command`、
>     「回复主题模板」`{productId}/{deviceId}/command/reply`。**已实测**两件事——
>     ① 平台发布的 `+MQTTPUBLISH:…,sensor-product/869413084698157/command,…` 不带 `/`，设备收到了；
>     ② 2026-09-27 平台「上行」栏出现过**不带** `/` 的 `sensor-product/869413084698157/command/reply`。
>   - **数据上报空间（带 `/`）**：属性上报页原文「订阅 `/{productId}/{deviceId}/properties/report`；
>     每 2 秒刷新最新值，折线 30 秒刷新一次」。
> - **曾经踩的坑（`#58`→`#62`）**：把这句"属性上报页要求带 `/`"错误地推广成"**发布方向**统一带 `/`"，
>   于是命令回复被发到了 `/{productId}/{deviceId}/command/reply`（5 段），而平台按 **4 段**过滤器认 →
>   平台上事件停在 `MQTT_PUBLISHED · WAITING_RESPONSE`，**20 秒判"指令超时"**，表现为"设备不回复"。
>   **教训：'/' 的归属是"主题级"事实，不是"方向级"约定**；换口径时指名到主题，别按方向一刀切。
> - **改法**：`app_config.h` 的 `APP_CFG_MODEM_TOPIC_PREFIX_*` ——**一条主题一个宏**，
>   平台要求哪一条换形态就改那一行（值只能是 `""` 或 `"/"`，有编译期护栏），
>   组件里的 `kTopicPrefix[]` 与这 10 个宏一一对应，不必碰组件代码。
> - **与主题名无关的那条踩坑仍然有效**：device 与后缀之间的 `/` 由**后缀字符串自带**（见 `kTopicSuffix[]` 的 NOTE）。
>   漏带会拼出 `…869413084698157command` 这种「中间少一个斜杠」的主题，模组照样回 `+MQTTSUBACK`
>   （订错了也显示成功），表现为「设备在线、订阅齐全、平台发布无回应」——**本仓库已实际踩过一次**（[[08-改动日志]] `#51`）。
> - **主题对了 ≠ 平台能看到数据**：上报**报文形状**也必须对。平台要的形状是
>   `{"deviceId":"<设备ID>","properties":{"<属性标识>":<值>,…}}`（2026-09-29 平台样例）；
>   旧的 `{"cmd":"data","seq":N,…}` 是自研协议，平台解析不出属性，属性页会一直「暂无属性上报」
>   ——**2026-09-29 已改**（见 [[08-改动日志]] `#77`）。属性标识符是否与平台物模型一致、上报频率
>   语义这两件事仍未对齐，见 [[11-平台接口需求]] 1.3，别和主题混在一起查。

### 请求（平台 → 设备）

```json
{"id":"<commandId>","command":"<不带 CR-LF 的 AT 命令>"}
```

- `id`：非空、平台唯一，设备**原样回显**。
- `command`：以 `AT` 开头、不含 CR/LF、UTF-8 不超过 256 字节；设备侧实际保存上限见 `APP_CFG_MODEM_DOWNLINK_COMMAND_SIZE`（当前 96，本设备 AT 行上限 `APP_CFG_AT_LINE_MAX` 只有 64，更长的命令本来就解析不了）。超限时回一条失败应答，不静默丢弃。
- 写参数命令里的引号在 JSON 中是转义的，例如 `AT+SN="VWA2608A0020"` 会以 `"command":"AT+SN=\"VWA2608A0020\""` 出现；设备侧用转义感知的提取器解析。
- `data` 字段（`>` 续传）当前**不支持**：本设备的命令都不需要续传。

### 回复（设备 → 平台）

成功（规则 3.3）：

```json
{"id":"42","ok":true,"data":"+SN:\"VWA2608A0020\"\r\nOK\r\n"}
```

失败（规则 3.4）：

```json
{"id":"42","ok":false,"error":"ERROR","data":"+CME ERROR:1\r\nERROR\r\n"}
```

- `data` 是**完整原始 AT 回复**，与串口逐字相同，只是按 JSON 规则把 `\r`、`\n`、`"`、`\` 转义。
- 失败时 `error` 字段固定为 `ERROR`（不填错误码）。本设备的失败形态是 `+CME ERROR:<n>`，它被当作详细行保留在 `data` 里，后面再补一行最终 `ERROR` 收尾（规则 4.2 的「可选错误行 + `ERROR`」）。**这一步只发生在 4G 回包上，串口输出不变。**
- 认不出来的命令（拼错、缺 `AT` 前缀）回 `{"id":…,"ok":false,"error":"ERROR","data":"ERROR\r\n"}`。
- `id` 取不到时用空串——平台按规则 3.5 会忽略这条回复，但设备侧不会因此卡住。

### 怎么验证（4G）

```powershell
# 无硬件时的最低保证：编译 + 链接
powershell -NoProfile -ExecutionPolicy Bypass -File sensor-node-fw\App\tools\smoke_build.ps1
```

**2026-09-27 已完成端到端实测（L5）**，证据如下：

```text
# 设备收到的下行（串口，诊断开关 APP_CFG_MODEM_TRACE_URC=1 打开时可见）
4g-core: +MQTTPUBLISH:0,1,0,1,sensor-product/869413084698157/command,67,{"id":"cmd-at-be346f1d-f60f-490d-ab4c-7698f43132af","command":"AT"}

# 设备发出的上行（平台「上行」栏）
topic: sensor-product/869413084698157/command/reply
body : {"id":"cmd-at-be346f1d-f60f-490d-ab4c-7698f43132af","ok":true,"data":"OK\r\n"}
```

判读要点：

1. `+MQTTPUBLISH` 的第 5 个字段是**主题原文**，第 6 个是**负载字节数**（67 = 上面那串 JSON 的长度），第 7 个才是负载；
2. 回包里的 `id` 与下行**逐字符相同**——平台靠它关联任务，改一个字符这条命令就永远完不成；
3. `data` 是 `OK\r\n`（JSON 里写作 `\r\n` 两个转义字符，不是物理换行）；
4. `ok:true` 只表示设备执行成功，与平台是否收到无关——所以平台侧必须订阅 `+/+/command/reply`；
5. **主题段数必须与平台过滤器一致**：`sensor-product/<pid>/<did>/command/reply` 是 **4 段**；
   若设备多发一个前导 `/` 变成 5 段，平台的 4 段过滤器匹配不到 → 平台上停在
   `MQTT_PUBLISHED · WAITING_RESPONSE`、20 秒判"指令超时"（2026-09-28 实测，见 [[08-改动日志]] `#64`）。

上板后按顺序自测：

| 步骤 | 从平台发 | 期望回到 `command/reply` |
|---|---|---|
| 1 | `{"id":"1","command":"AT"}` | `{"id":"1","ok":true,"data":"OK\r\n"}` |
| 2 | `{"id":"2","command":"AT+VER?"}` | `{"id":"2","ok":true,"data":"+VER:\"…\",\"…\"\r\nOK\r\n"}` |
| 3 | `{"id":"3","command":"AT+SN?"}` | `{"id":"3","ok":true,"data":"+SN:\"…\"\r\nOK\r\n"}`，且**改一个引号**：`{"id":"4","command":"AT+NOSUCH?"}` 应回 `ok:false`、`data` 以 `+CME ERROR:1\r\nERROR\r\n` 结尾 |

> [!warning] 排查这类问题的两个必备开关
> - `APP_CFG_MODEM_TRACE_URC = 1U`：把模组发来的 `+MQTT*` 行原样打进日志。组件对认不出的行是**静默丢弃**的，没有它就无法区分「消息没到模组」与「到了但名字不匹配」。
> - `APP_CFG_MODEM_TRACE_ENABLE = 1U`：连接计划每步的命令/应答诊断。主题步失败时现在会额外打出 `topic="<完整主题名>"`。
> 两者都只用于排障，正式版建议关掉（`TRACE_URC` 至少应关，它会在连接期持续刷屏）。

> [!note] 上板验证的前置条件
> 平台侧必须订阅 `+/+/command/reply`；设备侧必须真的订上 `{productId}/{deviceId}/command` —— 见本节顶部实测记录与 [[08-改动日志]] `#51`（主题少一个斜杠导致订阅静默失败的那次）。

## 参数存储（EEPROM）

调试口读写的 **7 个**参数都掉电保存在 I2C EEPROM（AT24C04）上：前 6 个是 BLE 身份配置，
第 7 个 `transintvl` 是**设备业务参数**（周期上报间隔）。表里另有一个**已退役**的槽位：

| 参数名 | 对应宏（默认值） | 容量 | 说明 |
|---|---|---:|---|
| `sn` | `APP_CFG_BLE_SN` | 24 | **设备序列号**：MQTT `deviceId` + 蓝牙认证应答的 `sn` + **蓝牙广播名**（三者同一个值） |
| ~~`name`~~ | —（随 `SN`） | 24 | **已退役**（2026-09-28）：广播名已并入 `SN`，本名字对外不存在（回 `+CME ERROR:1`）；槽位保留仅为介质兼容 |
| `pin` | `APP_CFG_BLE_PIN` | 12 | 小程序认证 PIN（凭据，日志不打印） |
| `uuid` | `APP_CFG_BLE_SERVICE_UUID` | 40 | Service UUID |
| `devname` | `APP_CFG_BLE_DEVICE_NAME` | 24 | 设备名（`device_info` 应答里的 `deviceName`） |
| `model` | `APP_CFG_BLE_MODEL_CODE` | 16 | 型号代号 |
| `batch` | `APP_CFG_BLE_BATCH_CODE` | 16 | 批次代号 |
| `transintvl` | `APP_CFG_MODEM_TRANS_INTERVAL_DEFAULT_TEXT` | 4 | **周期上报间隔**，分钟，1~20（数值型） |

> [!note] `transintvl` 与旧的云属性 `sample_interval`
> 设备**实际上报周期**只由 `transintvl` 决定（`AO_Modem` 每个 Process 周期从参数影子读一次，
> 见 `App/app/modem.c` 的 `reportIntervalMin()`），因此改完**立即生效**且掉电保持。
> 4G 组件里那份旧的云属性 `sample_interval`（1~1440 分钟、仅 RAM）**不再驱动上报节奏**，
> 只在每次进入在线态时被同步成当前值，供旧通道读回来核对。

记录格式、A/B 双槽与 CRC 见 `App/service/svc_param.h` 的文件头。`app_config.h` 里的宏只作为
**首次上电（介质空白或损坏）时的默认值**；只要介质上有一份 CRC 正确的记录，就以它为准。

周期输出：

```text

[I <uptime_ms>] heartbeat: alive, t=<秒> s
[I <uptime_ms>] ble: VG6328 on USART2 115200 8N1, waiting for module startup
[I <uptime_ms>] modem: MN316 on USART3 9600 8N1, waiting for module startup

```

`i2c` 那行的速率取自 `hi2c1.Init.ClockSpeed`（CubeMX 生成的 `Core/Src/i2c.c`），不是写死的文案。
`store:` 两行分别表示探测到器件、以及从介质读回了有效记录；介质空白或读失败时会改打
`store: blank media, using built-in defaults` / `store: no eeprom at 0x50 (...), using built-in defaults`。
**上板先看这两行**——它们直接回答「EEPROM 到底通没通、参数到底从哪来」。

其中传感器数据当前来自仿真驱动；温度使用 0.01 °C 定点值、湿度使用 0.1 %RH 定点值。BLE 那行在 `AO_Ble` 首次进入 `Active` 时打印一次，`USART2` 取自 `APP_CFG_BLE_UART_ID`；4G 那行在 `AO_Modem` 首次进入 `Active` 时打印一次，`USART3` 取自 `APP_CFG_MODEM_UART_ID`、后端名取自 `APP_CFG_MODEM_BACKEND`。

> [!important] 波特率打的是**实际生效值**，不是配置宏
> 两行的波特率都读自外设句柄（`BSP_bleUartBaud()` / `BSP_modemUartBaud()`），
> 而不是 `APP_CFG_*_UART_BAUD` 宏。原因见 [[03-资源分配#引脚分配]] 的说明：
> 2026-09-27 之前宏从未被写进外设，日志写着 `9600`、硬件跑 `115200`，
> 把真正的故障掩盖了整整一轮排查。**上板先核对这两行的波特率与实例**。

连接失败时的那行诊断也扩了字段（2026-09-27）：

```text
[W <ms>] modem: link failed reason=2 step=1 rx=0 tx_ovf=0 uart_err=0
```

`rx` 是累计收到的字节数：`rx=0 且 uart_err=0` = 线上一片安静（模组没供电 / 被摁在复位 /
线没接 / **波特率不对导致模组听不懂而不应答**）；`rx>0 且 uart_err>0` = 字节来了但成帧
失败，优先怀疑波特率。注意 `uart_err=0` **不能**单独用来排除波特率问题。

启动过程中原先还会出现一次旧文案 `sensor> idle (send 's' to start sampling)`；该指令早已删除，属误导性残留，2026-09-20 已改为 `sensor> idle`（采样仍由上电时投递的 `SYS_SENSOR_START_SIG` 自动启动）。

## Service 二进制帧

`App/service/svc_frame.{h,c}` 已实现内部组帧与严格解析，当前由 `AO_Sensor` 用于“组帧后立即解析”的自检，尚未直接作为 USART1 产品协议发送。

| 字段 | 长度 | 当前定义 |
|---|---:|---|
| SOF | 2 B | `0xAA 0x55` |
| LEN | 1 B | PAYLOAD 长度 |
| CMD | 1 B | 采样上报为 `0x10` |
| PAYLOAD | N B | 小端；采样载荷为温度 `int32` + 湿度 `uint16`，共 6 B |
| CRC16 | 2 B | CRC-16/MODBUS，初值 `0xFFFF`、多项式 `0xA001`，覆盖 LEN/CMD/PAYLOAD |

解析采用严格长度匹配，失败返回 `SVC_ERR_RANGE`、`SVC_ERR_CRC` 或 `SVC_ERR_NOMEM`。正式产品协议仍需定义地址、命令码全集、应答、超时、重传和重复帧策略。

## 怎么验证（AT 命令 + 参数存储）

需要硬件：USB-TTL 接 `PA9`(TX)/`PA10`(RX)，**115200 8N1，无流控**（见 [[#物理层]]）。

### 一键脚本（推荐）

工程自带 `App/tools/at_smoke.ps1`：固定顺序发一遍命令、逐条比对响应，并把
「宏配了但没生效」「回了 OK 却没落盘」这两类看不见的问题变成明确的 PASS/FAIL。
**默认只读**，不给 `-WriteTest` / `-WriteSn` 就绝不写 EEPROM。

```powershell

# 2) 只读检查（会提示你按一下复位键，以便抓启动横幅并核对波特率）
powershell -NoProfile -ExecutionPolicy Bypass -File sensor-node-fw\App\tools\at_smoke.ps1 -Port COM5

# 3) 追加无损写入测试：把当前 sn 原值再写一遍，验证「编码→页写→回读校验」整条路
powershell -NoProfile -ExecutionPolicy Bypass -File sensor-node-fw\App\tools\at_smoke.ps1 -Port COM5 -WriteTest

# 4) 有损：写入指定 SN（脚本会打印原值，便于还原）
powershell -NoProfile -ExecutionPolicy Bypass -File sensor-node-fw\App\tools\at_smoke.ps1 -Port COM5 -WriteSn VWA2608A0020

# 5) 板子已在跑、不想按复位键（跳过横幅检查）
powershell -NoProfile -ExecutionPolicy Bypass -File sensor-node-fw\App\tools\at_smoke.ps1 -Port COM5 -SkipBoot
```

退出码 `0` = 全部检查通过。**跑之前先关掉占着串口的程序**（串口助手 / Keil 的串口窗口 /
Xshell 等），否则会报 `Access to the port 'COMx' is denied`。

### 手工最小验证（5 步）

用任意串口助手即可，**每条命令都要带 CR/LF 行尾**（裸 `at` 已不再识别）。

| 步骤 | 发送 | 期望 | 这一步在验什么 |
|---|---|---|---|
| 1 | `AT` | `OK` | 通路是否活着 |
| 2 | `AT+SN?` | `+SN:"VWA2608A0013"` 后跟一行 `OK` | 介质空白时回的是 `app_config.h` 的默认值 |
| 3 | `AT+CFG?` | `+CFG:1,1,0,0,0,0,0,0` 后跟一行 `OK` | 第 2 位 `present=1` = EEPROM 应答了；第 3 位 `loaded=0` = 用的还是默认值 |
| 4 | `AT+SN="VWA2608A0020"` | 先 `OK`，随后日志 `store: saved ver=1 seq=1 slot=A …`；**值变了会接着出现 `system: rebooting now, src=identity`**，设备自动重启 | **`OK` 只代表「已受理」，落盘证据是那行 `saved`**；重启是「身份写成功」的正常现象，不是故障 |
| 5 | `AT+VER?` | `+VER:"<版本>","<编译日期>"` 后跟一行 `OK` | 固件是不是当前这份（版本与横幅同源） |
| 6 | 断电 3 秒再上电 → `AT+SN?`、`AT+CFG?` | `+SN:"VWA2608A0020"` / `loaded=1 ver=1` | **这一步才是「掉电保存」的验收**（第 4 步的自动重启已经顺带验过一次） |
| 7 | `AT+TRANSINTVL?` | `+TRANSINTVL:20` 后跟一行 `OK` | 数值型参数**不带引号**；出厂默认 20 分钟 |
| 8 | `AT+TRANSINTVL=?` | `+TRANSINTVL:(1,20)` 后跟一行 `OK` | 数值型报的是**范围**，不是字符数 |
| 9 | `AT+TRANSINTVL=5` → `AT+TRANSINTVL?` | 先 `OK`，再读到 `+TRANSINTVL:5`；随后日志 `store: saved ver=… seq=…` | 改完立即生效 + 异步落盘 |
| 10 | `AT+TRANSINTVL=0`（或 `=21`） | `+CME ERROR:2`，且 `AT+TRANSINTVL?` 仍是上一个值 | 越界**不写进影子**（写进去会污染 EEPROM） |
| 11 | 断电 3 秒再上电 → `AT+TRANSINTVL?` | 仍是第 9 步写入的值 | 业务参数的掉电保持 |
| 12 | `AT+SN="bad/id"`（含 `/`） | `+CME ERROR:2`，且 `AT+SN?` 不变 | 非法字符会破坏 MQTT 主题，**必须拒写**（写下就静默失效） |
| 13 | 板子仍是出厂默认 SN 时上电 | 横幅后出现 `modem: device SN unusable (len=…) -> 4G disabled; …`，且**没有** `cloud link ready` | 「未配置就不上网」是设计，不是故障（防同身份互踢） |
| 14 | 刷上合法 SN 后 → `AT+MQTTSUBACK` 里的主题串 | `sensor-product/<你刷的 SN>/command`（4 段、不带前导 `/`） | **这一步确认 `deviceId` 真的取自 SN**，且与平台侧配置逐字一致 |
| 15 | `AT+BLESVCUUID?` | `+BLESVCUUID:"CDAB0000-1234-5678-1234-56789ABCDEF0"` 后跟一行 `OK` | 回显名必须是 `+BLESVCUUID:`（平台按它匹配），不是 `+UUID:`；同一份值用 `AT+UUID?` 也能读到 |
| 16 | `AT+UUID="<新值>"`（串口） | `OK` → `store: saved` → **`system: rebooting now, src=identity`**（值变了才重启） | UUID 是身份类：**只允许串口写**、写成功自动重启（它只在上电时写进 VG6328） |

要恢复出厂默认值：发 `AT&F`（会连 `SN` 一起恢复成 `app_config.h` 的默认值 —— 产线上慎用，
见 [[08-改动日志]] `#67` 的遗留）。

### 判读要点

- **`OK` 只是「已受理」**：写参数是先改内存影子、再由 `AO_Store` 异步落盘。完整的落盘证据是
  `store: saved ver=… seq=… slot=…`，以及 `AT+CFG?` 里 `dirty` 回到 `0`。
- **槽序号有规律**：第一次写 A（`slot=A seq=1`），第二次写 B（`slot=B seq=2`），第三次又回到 A
  ——这就是 A/B 双槽交替；它的意义是「写到一半掉电时旧记录仍然完好」。看到槽序不交替，说明选槽逻辑坏了。
- **`ver` 只增不减**：`AT&F` 也是一次变更，会让它继续自增，不会倒回 0。
- **`AT+I2C?` 是异步的**：先立刻回 `OK`，约 0.3 s 后逐条打出 `+I2C:<7 位地址>`（最多 8 条），
  最后以 `+I2C:END` 收尾，另有一条人类可读的 `store: i2c scan done, N device(s)`。本板应只报出 `0x50`。
- **`pin` 是凭据（明文）**：测试记录、截图、工单里都不要带上它的值
  （[[AGENTS#4.2 其他工作区规则]] 的凭据纪律）。`at_smoke.ps1` 对 `AT+PIN?` 只校验格式、不打印值。
- **写参数要说清生效范围**：`AT+SN="…"` 立刻对后续读取生效，且它有**三个**用途：
  ① MQTT `clientId` 与 10 条主题里的 `deviceId`；② 蓝牙认证应答里的 `sn` 字段
  （`ble_protocol.c` 读的是参数影子的地址，改完立即生效）；③ **蓝牙广播名**——
  `ble.c` 把 `local_name` 也指向 `SVC_PARAM_BLE_SN`，由 VG6328 的 `AT+NAM=` 在启动配置时写进模组。
  ③ 只在**上电配置时**写一次，所以改完要重启才在广播里生效；而写 `SN` 会自动重启（见下条），
  两者正好闭环——**产线只需一条 `AT+SN=`，不必再单独刷广播名**。
  相比之下 `UUID` / `ULEN` 也是**启动时一次性写进模组**的，改了要重启才生效。
- **`SN` 写成功会自动重启**（值变了才会）：这是「身份参数」的统一规矩，不是故障。
  因为 `SN` 就是 `deviceId`（MQTT `clientId` + 10 条主题都是启动时拼的），
  **不重启就不会用新身份重新订阅**；重启前 `AO_System` 还会等参数落盘，避免"重启回来还是旧值"。
  `UUID` 同理（它只在上电时写进 VG6328，不重启广播里还是旧的）。
- **`AT+BLESVCUUID?` 是 `AT+UUID?` 的"带名字"版本**：读的是同一个值，但**回显名跟着命令走**
  （`+BLESVCUUID:"…"`），因为平台侧是按 `^\+BLESVCUUID:[^\r\n]*\r\nOK\r\n$` 匹配的。
  写入仍然只有 `AT+UUID="…"` 一种写法，而且**只允许串口**。
- **未刷 `SN` 的设备不会连 4G**：串口会打 `modem: device SN unusable reason=… pos=… ch=0x… len=… -> 4G disabled; …`，
  用 `AT+SN="<设备号>"` 刷一个合法值即可（会自动重启并上线）。这不是故障，是防"同身份互踢"。

### 常见现象对照

| 现象 | 多半是 |
|---|---|
| 完全没有响应 | 串口被别的程序占用 / 波特率不是 115200 / `PA9`-`PA10` 接反 / 板子没跑起来 |
| 回 `ERROR` | 命令拼错或没带行尾；写法不在 `AT`、`AT+<名>?`、`AT+<名>="<值>"`、`AT+<名>=?`、`AT+CFG?`、`AT+VER?`、`AT+CMD?`、`AT&F`、`AT+I2C?`、`AT+RST` / `AT+REBOOT` 之内 |
| 发了旧写法（`sn?`、`cfg!`）回 `ERROR` | **预期行为**：2026-09-27 起只认标准 AT 写法，旧语法不兼容 |
| `+CME ERROR:1` | 参数名不在 7 个之列（`SN` `PIN` `UUID` `DEVNAME` `MODEL` `BATCH` `TRANSINTVL`），或用了**退役的 `NAME`**（广播名就是 `SN`，改用 `AT+SN?`） |
| `AT+TRANSINTVL=…` 回 `+CME ERROR:2` | 值不是纯十进制数字，或不在 1~20 之内（分钟） |
| `+CME ERROR:3` | 上电后约 100 ms 内就发了写命令（启动加载还没结束），稍等再试 |
| `+CME ERROR:4` | **从云端写了 `AT+SN="…"`**：身份类参数只允许串口写（产线入口），云端只能 `AT+SN?` 读 |
| `AT+SN="…"` 回了 `OK` 却不见 `saved` | 落盘失败或介质不在：往前找 `store: save failed …` / `store: no eeprom …` |
| `AT+CFG?` 里第 2 位（`present`）为 0 | EEPROM 不应答：查 `PB6`/`PB7` 接线与上拉电阻、`A1`/`A2` 接法（用 `AT+I2C?` 扫一遍） |
| 开机日志的波特率与预期不符 | 说明宏没生效——启动横幅打的是**外设里的实际值**，见 [[03-资源分配#引脚分配]] |

## 边界行为

| 场景 | 行为 |
|---|---|
| RX 环形缓冲写满 | 丢弃新字节，不阻塞中断 |
| Node 事件队列满 | 投递不触发断言；后续接收事件可继续触发抽干 |
| AT 行超过上限（64） | 超出的字符被丢弃，整行按截断内容解析（解析器内部也会清行）；结果是回一条 `ERROR` |
| TX 日志队列写满 | 按配置丢弃并累计丢弃字节数 |
| EEPROM 不存在 / 总线不通 | 探测失败后回落到编译期默认值；写参数只改内存并回 `OK`，日志给 `save failed` |
| 写 EEPROM 失败 | 重试 → 补时钟恢复总线 → 再失败则保留内存值、`dirty` 清零、打一条 `save failed` |
| 产品级同步、寻址、确认、重传 | 尚未实现 |
