### #37 重构：调试口 AT 接口改写成**标准 AT 形态**（`AT` / `AT+NAME?` / `AT+NAME="v"` / `AT+NAME=?` / `AT+CFG?` / `AT&F` / `AT+I2C?`），旧自定义语法**不兼容**

- **类型**：重构（接口形态）+ 文档同步
- **变更**：
  - `App/service/svc_at.h` / `svc_at.c`：命令种类收敛为
    `PING / GET / SET / TEST / INFO / DEFAULTS / SCAN`；**强制 `AT` 前缀**，
    新增测试形式 `AT+<参数名>=?`；`AT+CFG?` / `AT+I2C?` 在通用 `AT+<名>?` 之前判定
    （否则会被当成参数名 `cfg` / `i2c`）；值允许带引号也允许不带（`copyValue()`）。

    它在 `AT+SN?` 的第 2 个字符处就会误触发并清空缓冲区。
  - `App/app/node.c` / `node.h`：`atExecute()` 的响应全部改写——
    成功回 `OK`（原小写 `ok`），读参数回 `+<NAME>:"<值>"`（参数名转大写，新增
    `nameUpper()`），测试形式回 `+<NAME>:(<容量−1>)`，`AT+CFG?` 回**位置式**
    `+CFG:rdy,present,loaded,dirty,ver,seq,ok,fail`（原 `+cfg:key=value`），
    失败回 `+CME ERROR:1/2/3/5`（原 `+err:<n>`）。启动横幅的命令清单从 2 行变 3 行。

    末尾 `+I2C:END` 收尾；最多上报 8 条（`STORE_SCAN_URC_MAX`，防止冲爆 512 B 日志环）；

  - `App/app/app_config.h`：仅注释更新（`AT+UUID="…"` 的长度估算、`AT+I2C?` 的措辞）；
    `APP_CFG_AT_ENABLE` 的初值写成 `(1U)` 与周围风格统一。
  - `App/tools/at_smoke.ps1`：全部命令换成新语法；新增 `Get-QuotedValue()` 剥引号；
    `AT+CFG?` 按**位置**取字段（第 3 位 = `loaded`、第 4 位 = `dirty`）；
    I2C 扫描改为等 `+I2C:END` 并断言出现 `+I2C:50`；新增 `AT+sn?`（大小写不敏感）与
    `AT+SN=?`（应回 `(23)`）两项检查；`cfg!` → `AT&F`。
  - 文档：`docs_sensor/06-协议格式.md`（AT 命令表、错误码表、`AT+CFG?` 字段表、横幅样例、

- **结案结论（依据用户 2026-09-27 的上板结果）**：

     （残留的 MQTT 客户端/会话），是**另一个独立问题**，不要与电信卡的网络问题混为一谈。

### #35 修复：日志格式化缓冲只有 96 字节，把 4G 诊断行砍在 `reason=` 之前 —— 提到 200，并把日志环提到 512

- **类型**：修复（诊断输出被静默截断）
- **变更**：`App/app/app_config.h`
  - `APP_CFG_LOG_FMT_BUF_SIZE` **96 → 200**，并写明它必须 ≥ 组件侧
    `MODEM_DIAG_LINE_MAX`（168）加前后缀；**改这个值时要一并核对 `MODEM_DIAG_LINE_MAX`**。
  - `APP_CFG_LOG_TX_RING_SIZE` **256 → 512**：日志缓冲变大后单条最长约 190 字符，
    环至少要装得下一条，否则环满时会把整行从中间丢掉，看起来仍像"固件在截断"。
- **原因**：用户贴出的上板日志每一行都断在同一个位置：
  `[D 83036] 4g-core: step 18/22 wait cmd="AT+MQTTCFG="43.154.189.189",48040,"" rx="+CME ERROR:800`
  —— 连引号和 `reason=` 都没了。数一下就对上：`[D 83036] `(10) + `4g-core: `(9) +
  `step 18/22 wait cmd="`(21) + 命令字段(36) + `rx="+CME ERROR:800`(18) = **94 字符**，
  而 `SVC_Log_Printf()` 的栈数组是 `APP_CFG_LOG_FMT_BUF_SIZE` = 96，`vsnprintf` 静默截断。
  **丢掉的正是 `reason=` 与 CME 错误码的最后一位**——排查时看到的是一行"没有结论的结论"。
  根子是两处口径不一致：组件按 `MODEM_DIAG_LINE_MAX`（168）认真拼行，日志层只给 95 字符。
  （本轮排查里这是第二次踩到同一类坑：`#28` 的 `rx` 只打首行也是"看的比拼的少"。）
- **验证**：
  - **L2**（`powershell -NoProfile -ExecutionPolicy Bypass -File sensor-node-fw\App\tools\smoke_build.ps1`）：
    **108 文件、0 error / 0 warning、链接通过**；`text 123490 / data 1752 / bss 15676`
    ——text 与 `#33` 完全一致（只改宏，不产生代码），**bss +256 B** 正是日志环 256 → 512 的增量；
    Flash 125242 B ≈ 47.8%，RAM 17428 B ≈ **35.5%** / 48 KB。该命令需在沙箱里提权执行。
  - **栈预算复核**：`APP_CFG_LOG_FMT_BUF_SIZE` 是 `SVC_Log_Printf()` 的**栈**数组（不是静态），
    由 96 涨到 200 = 每次日志调用多占 104 B 栈；主栈 4 KB、AO 调用深度浅，可接受，
    但这是本轮唯一涉及栈的改动，已在条目里记明。
  - **未上板**：完整的诊断行待复测。
- **遗留**：
  - **烧写后要拿两样东西**：
    ① 那一行的**完整内容**——特别是完整的 `+CME ERROR:800x`（4 位）与 `reason=`；
    ② 本次失败点**前移**的原因：同一张电信卡在更早的轮次里 `AT+MQTTCFG` 是**能通过**的
       （当时一路走到第 19 步 `AT+MQTTOPEN` 才失败），这次却连 6 次重试都不过。
       最可能是**插拔换卡留下的模组内部状态**（残留的 MQTT 客户端/会话）。
       `AT+MQTTDEL` 返回 8002 时被 `tolerate` 当成"没有客户端"放行，若模组其实还留着
       一个陈旧客户端，`AT+MQTTCFG` 就可能一直拒绝——这正好能解释"失败点前移"。
  - **值得观察的自愈路径**：`MQTT_OPEN`/`MQTT_CONFIG` 失败 → 连接计划失败 → AO 三次重连
       用尽后**给模组断电重启**（`power-cycling the module`）。断电重启会清掉模组内部状态，
       所以那条日志之后有可能自己恢复——上板时留意一下它是不是在自愈后走通了。
  - **仍然没拿到答案的那个问题**：换上中国移动 `cmiot` 那张卡时，第 19 步 `AT+MQTTOPEN`
    是通过了还是同样 `FAIL`？这一条直接决定"是卡的问题"还是"平台侧的问题"，
    比继续在固件里加诊断有价值得多。

### #4 修复：AT 应答结论被丢掉，命令无限重发（连接期与在线期都受影响）

- **类型**：修复
- **变更**：
  - `App/component/modem/modem_component.c`：`connectLoop()` 与 `readyLoop()` 不再以 `phase == MODEM_AT_WAITING` 作为读取 AT 引擎结论的前提，改为先取 `me->at.result`；只有结果仍为 `PENDING` 且命令在途时才调用 `ModemAt_Tick()` 推进超期判定，**且此时若仍为 `PENDING` 必须立即 `return` 等待**（第一版漏了这一句，见遗留）
  - `docs_sensor/03-资源分配.md`：L2 镜像数字更新
- **原因**：2026-09-19 上板实测（模组已能应答，`rx="OK"`）暴露出连接流程完全走不动：探活命令每 260 ms 被重发一次、`plan_step` 一直停在 0、AO 状态行持续显示 `at=WAITING/PENDING`。根因：应答经 `readPort → feedLine → ModemAt_Feed` 喂进 AT 引擎，而 `ModemAt_Feed()` 一旦命中期望标记或错误码就立即把 `phase` 置回 `MODEM_AT_IDLE`；等 `connectLoop()` / `readyLoop()` 去看结果时 `phase` 已经不是 `WAITING`，整个结论分支被跳过、`result` 无人消费。组件因此认为命令从未完成，在「没有在途命令」路径上不停重发同一条命令。该缺陷对连接期（每一步都卡住）与在线期（上报、命令应答被当成未发出而重发）同时成立，三个后端都受影响；NT26/MN316 从未上板验证过，所以一直没暴露。

  - 本修复的效果尚未上板确认；预期连接计划能正常逐级推进

### #11 L1 首次验证：AC6 编译全通过，链接因 microlib 与启动文件不匹配失败

- **类型**：验证 / 待修复
- **变更**：无代码改动；本条记录 L1 实测结果与诊断结论
- **原因**：按第 8 节要求用 Keil（ARM Compiler 6）做 L1 验证并留痕
- **验证**：
  - 编译阶段：45 个 `.c` 全部通过 AC6 **V6.23**，**0 error / 0 warning**
  - 链接阶段：失败，2 个错误 —— `L6218E: Undefined symbol __use_two_region_memory (referred from startup_stm32f103xe.o)`、`L6218E: Undefined symbol __initial_sp (referred from entry2.o)`；目标未生成，无 Flash/RAM 数字
  - 诊断（查 `MDK-ARM/sensor-node-fw.uvprojx` 与 `startup_stm32f103xe.s`）：
    - 工程文件磁盘版本里**没有** `<useMicroLib>` 标签（磁盘上未启用 microlib，`<uAC6>1</uAC6>` 正常）
    - 但链接器引入了 microlib 的 `entry2.o`（它需要 `__initial_sp`）
    - 而 `startup_stm32f103xe.o` 走的是**标准库分支**（第 330 行 `IF :DEF:__MICROLIB` 未成立 → `IMPORT __use_two_region_memory`，且不 `EXPORT __initial_sp`）
    - 结论：µVision 里启用了 **Use MicroLIB**（很可能尚未保存回工程文件），而启动文件的 `.o` 是按标准库分支汇编的，于是两个符号都缺。与本次新增的代码无关
  - 修复建议（二选一，需人工在 µVision 操作）：
    1. **取消勾选** `Options for Target → Target → Code Generation → Use MicroLIB`，然后 **Rebuild**（推荐：与本工程原有设置一致，`vsnprintf` 支持最完整）
    2. 保留 microlib，但必须 **Rebuild All**（不是 Build），让启动文件带 `__MICROLIB` 重新汇编
